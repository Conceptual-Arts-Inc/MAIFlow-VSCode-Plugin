# MAIFlow VS Code Extension Specification

Status: Proposed  
Target project: `maiflow-vscode-extension`  
Date: 2026-09-16

## 1. Decision summary

Build a small, platform-only VS Code extension that brings MAIFlow tasks into the editor through a `MAIFlow` view and VS Code commands.

The extension should use MAIFlow's documented MCP endpoint as its only application integration boundary:

```text
https://app.maiflow.org/api/mcp
```

Authentication must use the same user-created `mf_live_...` MAIFlow API token used by MCP. There is no separate extension key. The extension must store that token with the VS Code Secret Storage API (`vscode.SecretStorage`), never in workspace files, logs, URLs, source code, or the extension package. The extension must not implement Keycloak login, read MAIFlow browser cookies, or access Totalum/PostgreSQL directly.

The first release should be a focused task-management client. It should not attempt to become a language extension, code analyzer, or replacement for GitHub Copilot or other AI assistants. Compatible AI tooling can be configured separately to use MAIFlow as a remote MCP server; the extension may provide setup guidance for that workflow.

## 2. Repository baseline

The actual starter is `maiflow-vscode-extension`:

- TypeScript production sources under `src/`.
- VS Code Extension API with `engines.vscode` targeting a recent stable release (e.g. `^1.96.0` or later).
- TypeScript, Node.js, and the standard VS Code extension development stack (`@types/vscode`, `vscode` module).
- Platform-only dependency: the VS Code Extension API; no language-specific or task-extension hard dependencies for v1.
- Generated sample view/command contributions in `package.json`.
- Generated placeholder metadata and sample code that should be replaced before implementation.

The generated sample code and placeholder metadata should be replaced before implementation. Use the modern VS Code Extension API and contribution points; do not rely on deprecated APIs.

## 3. Goals and non-goals

### Goals

1. Let a developer see their MAIFlow workspace without leaving the editor.
2. Let a developer create a task from the editor.
3. Let a developer update task status and score inputs from the editor.
4. Let a developer open the full MAIFlow task or flow page in a browser.
5. Associate a VS Code workspace with a MAIFlow flow and optional MAIFlow project.
6. Keep network work cancellable and off the UI thread.
7. Provide clear handling for authentication, paid-plan, permission, validation, and network failures.
8. Preserve a clean boundary so the MAIFlow API can evolve without coupling UI code to JSON-RPC details.

### Non-goals for v1

- Keycloak login, password handling, or session-cookie reuse.
- Direct access to MAIFlow's database or internal server modules.
- App Builder, Voiceflow, billing, admin, or token-management API operations.
- Code inspections, completion, refactoring, syntax highlighting, or language support.
- Uploading source code or selected editor text automatically.
- Continuous high-frequency polling.
- A hard dependency on GitHub Copilot, Copilot Chat, or any other AI extension.

## 4. MAIFlow integration contract

MAIFlow exposes a stateless Streamable HTTP MCP endpoint. Its current server supports protocol versions `2025-06-18`, `2025-03-26`, and `2024-11-05`, and exposes two tools:

- `maiflow_capabilities` — returns the allowlisted MAIFlow routes and methods.
- `maiflow_api_request` — calls an authorized relative `/api/...` route while forwarding the same bearer token.

The extension should implement a narrow typed client over those tools rather than expose arbitrary JSON-RPC calls throughout the UI.

### Request behavior

Every request must:

- `POST` one JSON-RPC request object to the configured MCP endpoint.
- Send `Authorization: Bearer <the same MAIFlow MCP token>`.
- Send `Content-Type: application/json` and `Accept: application/json`.
- Use a fresh request ID for each call.
- Use `initialize` before the first capability or API call after configuration changes.
- Treat the server as sessionless. Do not require or persist an MCP session ID.
- Enforce HTTPS for non-localhost endpoints; allow `http://localhost` and loopback URLs for development.

Initialization payload:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": {},
    "clientInfo": {
      "name": "maiflow-vscode-extension",
      "version": "<extension-version>"
    }
  }
}
```

The client should call `maiflow_capabilities` during **Test Connection** and cache the returned route catalog for the current application session. It should still use typed route methods so a server-side allowlist change produces a controlled error instead of an unsafe fallback.

### v1 typed operations

```
| Extension operation                                 | MCP tool call         | MAIFlow route/body                                                                                                             |
| --------------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Load workspace                                      | `maiflow_api_request` | `GET /api/workspace/tasks`                                                                                                     |
| Load small chrome state, if notifications are added | `maiflow_api_request` | `GET /api/workspace/chrome`                                                                                                    |
| Create task                                         | `maiflow_api_request` | `POST /api/tasks` with `title`, `flowId`, optional `description`, `priority`, `urgency`, `impact`, `effortPoints`, `projectId` |
| Update task                                         | `maiflow_api_request` | `PUT /api/tasks/:taskId` with any supported mutable fields                                                                     |
| Delete task, if enabled later                       | `maiflow_api_request` | `DELETE /api/tasks/:taskId`, confirmation required                                                                             |
| Create flow, if enabled later                       | `maiflow_api_request` | `POST /api/flows`                                                                                                              |
| Create project, if enabled later                    | `maiflow_api_request` | `POST /api/projects`                                                                                                           |
```

The workspace response contains `viewer`, `organizations`, `projects`, `flows`, `tasks`, and `tasksComplete`. The extension should map only the fields it renders and tolerate additional server fields. Current task statuses are `todo`, `in_progress`, `blocked`, and `completed`; task scores are integers from `0` through `10`.

### Error mapping

The client must preserve the upstream status and user-facing message while keeping credentials out of diagnostics.

```
| Status                                    | UI behavior                                                                                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| `401`                                     | “MAIFlow token is invalid, revoked, or missing.” Offer Settings and Profile links.                            |
| `402`                                     | “MAIFlow MCP access requires an active Personal or Team plan.” Offer Billing/Profile link.                    |
| `403`                                     | Explain that the account, verification, organization membership, role, or entitlement prevents the operation. |
| `400`                                     | Show validation feedback and do not retry.                                                                    |
| `404`                                     | Refresh once; if still missing, report that the task/flow no longer exists or is inaccessible.                |
| `429`, `5xx`, timeout, connection failure | Offer retry. Retry reads/capabilities only; never blindly retry a write.                                      |
| Malformed JSON-RPC or unexpected response | Report a generic protocol error and include a redacted diagnostic entry in the extension Output channel.      |
```

## 5. User experience

### Configuration

Add settings under `maiflow` (Settings UI and `settings.json`) with:

- Server URL, defaulting to `https://app.maiflow.org/api/mcp`.
- API token stored only via Secret Storage for the same token created in MAIFlow Profile → API access and used by MCP.
- **Test Connection** command.
- **Open MAIFlow Profile** command, opening the browser to the configured app origin's Profile page.
- A redacted token prefix/status and last successful connection time.
- A short warning that rotating or revoking a MAIFlow token invalidates existing clients, including this extension and MCP clients.

Persist the server URL and non-secret metadata using VS Code configuration (user or workspace scope as appropriate). Persist the token only through `vscode.SecretStorage`, keyed by a normalized endpoint identity. Never serialize the plaintext token in settings, workspace state, or global state. Do not attempt to read or mutate other extensions' private MCP configuration; both integrations use the same MAIFlow credential independently.

### MAIFlow view

Use the short, title-case name `MAIFlow`. The view should be a tree/list-oriented Side Bar view (Activity Bar contribution) with a concise title-bar toolbar:

- Refresh.
- Flow/project filter.
- Create task.
- Open Settings.
- Open current selection in MAIFlow.

Suggested content layout:

```text
MAIFlow
├── Filter / Refresh / Create
├── Current task or selected flow
└── Task list
    ├── status chip · title · flow/project · score
    └── assignee · priority · updated time
```

Each task opens a detail view or panel containing title, description, status, priority, urgency, impact, effort, assignee, flow, project, and engine score. Mutations must be explicit and show a success/error result; the list refreshes after a successful write.

Required states:

- Not configured: empty state with **Configure MAIFlow**.
- Loading: progress indicator and disabled duplicate actions.
- Loaded: task list and filters.
- Empty: explain that no reachable tasks were returned.
- Stale: show cached data with a visible refresh/error affordance.
- Unauthorized/paid-plan/permission failure: actionable message with the appropriate settings/profile/billing action.
- Offline or timeout: cached data remains visible when available.

The view should not be shown by default for an unconfigured workspace unless the user explicitly opens it from a MAIFlow command. Use contribution `when` clauses and view visibility to avoid presenting irrelevant UI in every workspace.

### Workspace mapping

Add a workspace-level mapping in Settings or from the view:

- MAIFlow flow ID, required for creating tasks.
- Optional MAIFlow project ID.
- Optional “use this mapping for new tasks” flag.

Store mapping IDs in workspace state, preferably user-specific workspace state. Store no API token or token-derived data in workspace files. If a future team workflow needs VCS sharing, add an explicit opt-in mapping file with only non-secret IDs.

### Editor context safety

The default create-task flow may use editor metadata such as workspace folder name, repository name, branch name, and current file path. It must not send source code, selected text, whole-file contents, or diagnostics unless the user explicitly opts in for that particular request. Any opt-in code context must be visibly summarized before submission.

## 6. Technical architecture

Use TypeScript for new implementation. TypeScript is the standard fit for the VS Code Extension API, structured cancellation, and async work on the extension host. Use the Tree View API (or a Webview for richer layout) for the interactive view; prefer native contribution points for settings and commands.

Recommended package structure:

```text
src/
├── commands/
│   ├── configureMAIFlow.ts
│   ├── createTask.ts
│   ├── refreshTasks.ts
│   └── openTask.ts
├── api/
│   ├── mcpHttpTransport.ts
│   ├── mcpClient.ts
│   ├── mcpModels.ts
│   ├── maiflowApi.ts
│   └── maiflowApiError.ts
├── model/
│   ├── workspaceSnapshot.ts
│   ├── taskSummary.ts
│   ├── flowSummary.ts
│   └── projectSummary.ts
├── services/
│   ├── maiflowWorkspaceService.ts
│   ├── maiflowSettings.ts
│   └── maiflowTokenStore.ts
├── views/
│   ├── maiflowTreeDataProvider.ts
│   ├── maiflowView.ts
│   └── taskDetail.ts
└── extension.ts
```

Responsibilities:

- `mcpHttpTransport`: endpoint validation, headers, timeouts, JSON-RPC envelope, response decoding, redacted logging.
- `mcpClient`: initialize, call tool, normalize JSON-RPC errors.
- `maiflowApi`: typed workspace/task/flow/project operations and route-specific payloads.
- `maiflowWorkspaceService`: workspace-scoped cache, refresh state, mutations, and UI-facing observable state.
- `maiflowSettings`: server URL and non-secret connection preferences.
- `maiflowTokenStore`: Secret Storage access only; no token getter exposed to UI logging or model serialization.
- View/command classes: render state and dispatch actions; no raw HTTP or JSON parsing.

Use workspace-scoped services and cancellation tokens for workspace-lifetime work. Network requests must run asynchronously and be cancellable when the workspace closes or the extension deactivates. UI updates must keep the editor responsive. Commands must keep update/enablement logic fast.

For HTTP, use a public Node/platform-supported client (e.g. built-in `fetch`) and respect system/proxy settings where feasible. Do not depend on other extensions' internal classes or on AI assistant internals. Pin any third-party JSON dependency explicitly if the selected target does not provide a stable compatible JSON API.

Cache policy:

- In-memory cache for the current session and workspace.
- No persistence of task descriptions, comments, attachments, or token-bearing responses by default.
- Refresh on view visibility, manual refresh, successful mutation, and an optional conservative interval only while the view is visible.
- Cancel and replace an in-flight refresh rather than allowing overlapping reads.

## 7. Extension metadata and package.json changes

Before the first release:

1. Change the stable extension ID to a final form such as `conceptualarts.maiflow` (or equivalent) before publishing. Once published, do not change it.
2. Change the display name to `MAIFlow`.
3. Replace the placeholder publisher and description with Conceptual Arts/MAIFlow information and a support URL.
4. Keep the VS Code Extension API as the only required platform dependency for v1.
5. Set `engines.vscode` to the minimum supported version and omit an upper bound unless a verified compatibility break requires a bounded release.
6. Use a current TypeScript and Node toolchain compatible with the target VS Code version.
7. Keep production dependencies minimal; avoid bundling unnecessary native modules.
8. Replace the sample view and command registrations with MAIFlow registrations.
9. Add a dedicated monochrome view icon; the existing colored logo can remain the Marketplace/extension icon.
10. Do not add hard dependencies on Tasks, Copilot, or other optional integrations until implemented and tested as separately guarded features.

Expected contribution points for v1:

- View container and tree view (or webview).
- Configuration properties under `maiflow.*`.
- Workspace/global state usage for non-secret data.
- Configure/create/refresh/open-task commands.
- Optional activation only when configuration exists or the view is opened; do not perform a blocking network call during extension activation.

Use modern Secret Storage, configuration, and state APIs. Do not use deprecated contribution points or APIs.

## 8. Optional native Tasks integration

After the view vertical slice is stable, evaluate implementing optional integration with VS Code task/workspace concepts:

- Lightweight status bar or “current task” representation mapped from MAIFlow's four statuses.
- Optional commands that surface MAIFlow tasks in a tasks-style workflow.
- Secret Storage for the same API token.
- Optional dependency on any task-related extension, with graceful behavior when it is not installed.

This would allow MAIFlow tasks to participate more deeply in the editor workflow. It should remain a later phase because it introduces another surface and potential dependency. The MAIFlow view remains the primary UX until the integration has proven useful.

## 9. AI assistant / MCP client relationship

Compatible AI tooling supports remote Streamable HTTP MCP servers. A user can configure MAIFlow independently with a JSON shape such as:

```json
{
  "mcpServers": {
    "maiflow": {
      "url": "https://app.maiflow.org/api/mcp",
      "headers": {
        "Authorization": "Bearer mf_live_<the-same-token>"
      }
    }
  }
}
```

The extension should provide a documentation link and a redacted copyable template, but should not require any AI extension to be installed. Do not assume a public API exists for another product's MCP settings page; validate any “configure automatically” idea against the exact target product before implementing it. A future release may add a dedicated command that opens the relevant settings page if a stable public path is available.

## 10. Testing and acceptance

### Automated tests

- JSON-RPC request/response serialization and protocol-version negotiation.
- MCP tool-call extraction, including `structuredContent` and `isError` responses.
- Endpoint normalization and localhost/HTTPS validation.
- Error/status mapping and message redaction.
- Token-store behavior using a test double for Secret Storage; assert plaintext tokens never enter settings, workspace state, or logs.
- Workspace/task mapping with missing and additional fields.
- Create/update payload validation and status mapping.
- Settings persistence and workspace mapping persistence.
- Workspace service cancellation and refresh coalescing.
- View state rendering in unit or integration tests (e.g. Extension Development Host / `@vscode/test-electron`).

### Opt-in integration tests

Support environment variables such as `MAIFLOW_EXTENSION_E2E_URL` and `MAIFLOW_EXTENSION_E2E_TOKEN`, never committed to the repository. Read-only tests should cover `initialize`, `maiflow_capabilities`, and workspace loading. Write tests must be disabled unless explicitly enabled and should use a disposable test account/flow.

### Manual acceptance matrix

1. Fresh install with no configuration shows a useful setup state.
2. Valid token and paid account load flows, projects, and tasks.
3. Invalid/revoked token shows actionable `401` guidance without exposing the secret.
4. Free/lapsed account shows actionable `402` guidance.
5. Inaccessible organization/task shows `403`/`404` guidance.
6. Create task succeeds and appears after refresh.
7. Update status succeeds and preserves other fields.
8. Timeout/offline mode keeps cached data visible and offers retry.
9. Editor close/extension deactivate cancels network work cleanly.
10. The extension runs in VS Code (and optionally compatible hosts) without a language-specific dependency.

### Required checks

```text
npm test   (or project equivalent)
vsce package
```

Also exercise **Run Extension** / Extension Development Host. Validate the packaged VSIX and Marketplace readiness before publishing.

## 11. Delivery phases

### Phase 0 — Replace the scaffold

- Rename metadata and packages.
- Remove the sample view/commands.
- Add settings, token store, service skeleton, and test fixtures.
- Confirm Extension Development Host, package, and basic tests work.

### Phase 1 — Vertical slice

- Configure endpoint/token.
- Test connection through MCP initialization and capabilities.
- Load and render `/api/workspace/tasks`.
- Handle all documented error classes.

### Phase 2 — Task workflow

- Create task.
- Update task status and score inputs.
- Add task detail panel, browser links, filters, cache, and refresh coalescing.

### Phase 3 — Editor workflow integration

- Workspace-to-flow/project mapping.
- Safe editor metadata context.
- Evaluate optional Tasks-style / status-bar integration.
- Add AI/MCP setup guidance.

### Phase 4 — Release hardening

- Marketplace description, support link, screenshots, and changelog.
- Publishing secrets only in CI/local environment configuration.
- Compatibility review for the declared VS Code version range.
- Opt-in production telemetry only if a privacy policy and user consent model are agreed; otherwise rely on redacted local Output channel logs.

## 12. Risks and decisions to confirm during implementation

- MAIFlow currently has one active API token per user; token rotation invalidates the old token. The UI must make that consequence clear for this extension and other MCP clients using the same token.
- The MCP endpoint is the documented boundary, but its current server is intentionally sessionless and returns JSON responses. Keep transport details isolated so a future Streamable HTTP session/streaming change affects one module.
- Workspace loading is intentionally broad. Add pagination or a dedicated lightweight read route if large workspaces make the view slow.
- The full MAIFlow web app uses paths such as `/tasks/:taskId`, but browser deep-link construction should be confirmed against the deployed app before release.
- Optional Tasks or AI integration may be valuable but should not delay the first usable view release.
